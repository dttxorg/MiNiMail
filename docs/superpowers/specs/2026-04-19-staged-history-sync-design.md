# 分阶段历史同步设计

日期：2026-04-19

## 背景

当前邮件客户端在首次同步 Gmail 或其它历史邮件较多的账号时，会直接按当前“邮件历史范围”执行一次完整历史抓取。即使内部已经做了分页，这条链路对用户的观感仍然像“长时间卡住”，因为：

1. 列表必须等待较大时间窗口的同步结果才逐步变得完整。
2. `all`、`6mo` 这类大窗口在网络不稳定时更容易触发超时或连续重试。
3. 用户无法直观看到“软件正在逐步扩展历史范围”，会误以为应用卡死或黑屏。

目标是把首次历史同步改成“分阶段扩展窗口”的体验，同时保持现有增量刷新和缓存语义清晰。

## 目标

### 用户目标

1. 首次同步时，最近邮件应尽快出现在列表里。
2. 历史范围越大，客户端应该越早先显示近邮件，再逐步补更久的历史，而不是一直空等。
3. 缓存范围必须是最终保留边界，优先级高于历史范围。
4. 后续刷新仍然以增量为主，不重复跑完整历史。

### 技术目标

1. 复用现有 `syncMails()` / `fetchFromImap()` / SQLite cache，而不是再造一套同步体系。
2. 明确区分：
   - 服务器历史拉取边界
   - 本地缓存保留边界
   - 后续刷新增量边界
3. 同步过程中可逐段更新 UI，避免长时间“假死”。
4. 保留对 `all` 的支持，但不允许一次性整段阻塞式抓取。

## 非目标

1. 本次不改变“手动刷新”和“自动刷新”的基本入口。
2. 本次不改变正文按需抓取策略。
3. 本次不新增后台守护进程或独立队列服务。
4. 本次不引入新的同步数据库表。

## 核心语义

### 1. 邮件历史范围

`mailFetchHistoryRange` 表示“服务器历史拉取最远边界”。

分段规则如下：

- `7d`：只拉 `7天`
- `15d`：拉 `7天 → 15天`
- `1mo`：拉 `7天 → 15天 → 1个月`
- `6mo`：拉 `7天 → 15天 → 1个月 → 6个月`
- `1y`：拉 `7天 → 15天 → 1个月 → 6个月 → 1年`
- `all`：拉 `7天 → 15天 → 1个月 → 6个月 → 1年 → 全部`

这里的“全部”表示不再设置 `historySince` 上限，由 IMAP 分页拉完整列表。

### 2. 邮件缓存范围

`mailCacheRange` 表示“本地缓存允许保留的最长时间窗口”，优先级最高。

缓存范围规则：

- `3d`
- `7d`
- `1mo`
- `6mo`
- `all`

即使历史范围更大，只要缓存范围更小，最终写入并保留在本地缓存中的邮件也必须受缓存范围限制。

例子：

- 历史范围：`all`
- 缓存范围：`7d`

行为：

1. 服务器可以按阶段去尝试更大的历史窗口。
2. 但本地 cache 和最终长期保留列表只允许保留 7 天内邮件。
3. 因此不会因为历史范围设成 `all` 就让本地缓存无限膨胀。

### 3. 首次同步与后续刷新

只有以下情形启用“分阶段历史同步”：

1. 账号/文件夹当前没有任何本地缓存。
2. 用户显式要求按历史范围强制重建当前视图。

后续刷新保持现有语义：

1. 默认只拉增量。
2. 不再重复走完整分阶段历史同步。
3. 若用户改了历史范围，本次不自动拉取；仍然由手动刷新触发新的历史边界重建。

## 方案比较

### 方案 A：单次大窗口分页同步

优点：

- 实现最简单。

缺点：

- 仍然会给用户“长时间卡住”的感受。
- 对大邮箱或 Gmail 首次拉取不友好。

### 方案 B：分阶段历史同步

优点：

- 最近邮件最先出现，体验显著更平滑。
- 网络慢时至少能先拿到近邮件。
- 更符合“客户端正在逐层扩展历史”的心理预期。

缺点：

- 状态管理比单次同步更复杂。

### 方案 C：只拉列表 envelope，正文完全后置

优点：

- 列表能更快亮起来。

缺点：

- 与当前正文体验和现有点击加载修复方向冲突。
- 不能解决历史窗口同步的感知问题。

结论：采用方案 B。

## 架构改动

### 主进程

在 `src/main/services/mailService.ts` 中新增“分阶段同步”能力。

新增概念：

1. `buildHistoryStages(historyRange: MailHistoryRange): MailHistoryRange[]`
2. `syncMailsStaged(...)`
3. 每阶段完成后返回当前累计结果和阶段状态

`syncMails()` 不直接废弃，而是：

- 增量刷新路径继续走现有 `syncMails()`
- 首次/强制历史路径改走 `syncMailsStaged()`

### 渲染进程

`App.tsx` 需要能识别同步是否为 staged：

1. 每完成一段，刷新当前视图缓存
2. 列表顶部显示轻量状态提示，例如：
   - `正在同步最近 7 天邮件`
   - `正在扩展到 15 天`
   - `正在扩展到 1 个月`
   - `正在同步全部历史邮件`

此提示为非阻塞，不替代列表。

### 共享层

在 `src/shared/mailSyncSettings.ts` 中补充：

1. 历史范围到阶段数组的映射
2. 缓存范围优先裁剪辅助函数

## 数据流

### 首次同步/无缓存

1. 用户进入账号/文件夹
2. 渲染层发现无缓存
3. 调用 staged 历史同步
4. 主进程按阶段执行：
   - 7天
   - 15天
   - 1个月
   - ...
5. 每阶段完成：
   - 用当前阶段结果 upsert cache
   - 立刻裁剪超过缓存范围的邮件
   - 回传阶段完成事件
6. 渲染层收到阶段完成事件后重载当前缓存列表
7. 最终阶段完成，提示结束

### 手动刷新

1. 若当前视图已有缓存，默认只做增量刷新
2. 若当前视图无缓存，走 staged 历史同步
3. 若未来需要“强制按历史范围重建”，可以在刷新按钮上追加次级动作，但本次不做 UI 扩展

## 关键规则

### 1. 缓存范围优先级最高

任何阶段完成后都必须立即执行 cache prune。

原因：

1. 防止 `all` / `1y` 导致 SQLite 急剧膨胀
2. 保证“缓存范围”语义稳定、可预期

### 2. 阶段结果必须可见

每个阶段完成后，渲染层应立刻看到更多邮件，而不是等最终阶段。

### 3. 增量刷新不走 staged

否则会把每次刷新都变成复杂长任务。

### 4. Gmail 等慢账号必须支持中途中止

如果用户切换账号、切换文件夹或关闭窗口，正在进行的 staged 同步需要标记为过期结果，后续阶段结果不得再覆盖新视图。

## UI 设计

### 列表顶部状态条

位置：邮件列表顶部搜索栏下方，轻量展示。

内容示例：

- `正在同步最近 7 天邮件`
- `正在扩展到 15 天`
- `正在扩展到 1 个月`
- `正在扩展到 6 个月`
- `正在同步全部历史邮件`

要求：

1. 不阻塞列表滚动和点击
2. 文案跟随软件语言
3. 阶段完成后自动消失

## 错误处理

### 网络超时

若某一阶段超时：

1. 保留已经完成阶段的缓存和列表
2. 给出轻量错误 toast
3. 本次 staged 任务终止

### 账号 OAuth 失效

1. 直接中断该账号后续阶段
2. 不影响其它账号
3. 保留已完成阶段结果

### 用户中途切换视图

1. 原阶段任务标记为 stale
2. 不再把旧阶段结果写回当前视图 UI
3. 主进程任务可继续完成写 cache，或在后续优化里支持取消；本次先保证 UI 不错乱

## 风险与缓解

### 风险 1：阶段写回导致重复邮件闪烁

缓解：

每次阶段完成都通过现有 cache upsert + `loadCached` 重载，避免前端自己拼接重复数据。

### 风险 2：阶段任务与正文点击加载并发

缓解：

正文点击加载继续独立走 `fetchFull`，不等待 staged 历史任务；同时 staged 只更新列表和 cache，不直接改当前选中详情对象。

### 风险 3：全部历史在超大邮箱仍然很慢

缓解：

至少最近 7 天会优先可见，用户感知不再是整段卡死。
